## Phase 4: User Story 2 — Weekly analytics stay current (P2)

**Goal**: Recomputed volume figures appear on an open dashboard without a reload.

**Independent Test**: With the dashboard open on a week, cause that week's volume
to be recomputed; the figures change while the dashboard stays on that week.

## Phase 8: Ingest durability

**Why this is in *this* spec**: `IngestionService.ingest` performs four writes
across three systems — GridFS, `raw_uploads`, the `workouts` row, then a
RabbitMQ publish — with no atomicity between them. That predates this feature,
but this feature is what makes the worst case visible. A workout whose
`workout.uploaded` publish is lost never reaches a terminal status, so before
spec 004 it sat in a list wearing a grey badge, and after it sits in the
in-flight modal **forever** — which SC-012 forbids ("zero workouts remain in
the in-flight surface after processing has reached a terminal outcome").

The publish is not merely untransactional, it is unconfirmed:
`rabbitmq-publisher.service.ts:18` uses `createChannel()` rather than
`createConfirmChannel()`, and `publish()` is synchronous and returns `void`. A
dropped connection loses the event with no exception raised anywhere.

**Three increments, deliberately overlapping.** Each is useful alone; together
they are defence in depth. They can ship independently of the user stories.

### Increment 1 — compensating action (closes both failure halves, cheaply)

- [X] T054 Switch `apps/api/src/events/rabbitmq-publisher.service.ts` to `createConfirmChannel()` and make `publish()` async and awaited, so a broker that never acknowledges raises instead of silently dropping. Note this alone makes things *worse* without T055: the workout row is already saved when the publish fails, so a client retry would create a duplicate
- [X] T055 Wrap the write sequence in `apps/api/src/workouts/ingestion.service.ts` so a failure after the Mongo writes deletes what it created (GridFS blobs, the `raw_uploads` doc, the `workouts` row) and returns `503`. The user then sees either "it worked" or "it failed" — never a half-written workout. **This is a compensating action, not a saga**: one method drives the whole sequence and its undo, with no second participant and no messages between steps. If anything, that makes it orchestration; the project's actual choreography is `workout.uploaded → parser → workout.parsed → analytics`, where nobody holds the overall picture. Implemented as `storeOrUndo` (the boundary) plus `undo` (the reversal, newest write first), with a class-level call-order comment since the flow spans three systems and two other files. **The boundary stops before the notification publish** — `publishNotification` already never throws, so including it would be harmless today and wrong tomorrow: FR-030's guarantee would then rest on a promise made in another package rather than on where the code sits, and a durably stored workout must survive every notification path being broken. Two things the task did not ask for but the audit made unavoidable: the image upload used `Promise.all`, which **discards the refs of uploads that already succeeded** when one rejects — those blobs become unreachable, since no `raw_uploads` doc will ever name them, so `undo` could not have cleaned a partial upload at all; `allSettled` plus collecting the fulfilled refs before rethrowing is what makes that half possible. And the stale comment claiming a GridFS failure "surfaces as a clean 500" was corrected — it is now a 503 with cleanup, which is also the more honest code for "Mongo is unavailable". `undo` **never throws**: a failed cleanup must not replace the original error, since the caller needs "it failed, retrying is safe" far more than it needs to know which half of the rollback missed. **The T056 decision, recorded now while the context is fresh**: if the compensation itself fails, the orphan is logged and accepted, and nothing retries it — a chosen limit, not an oversight, because an orphan costs storage and no correctness, and a durable cleanup queue is a second outbox to justify the rarer half of a rare case. The `workouts` row is undone first because it is the only one of the three a user can see; if the sequence breaks partway it should break on the invisible end. ## Implementation Strategy

**MVP = Phase 1 + Phase 2 + Phase 3 (US1)** — T001–T034. That delivers the gap
this feature exists to close: a logged workout resolves on screen without a
reload, and the dashboard's list and chart stop disagreeing.

**Why the infrastructure comes first and is user-invisible**: Phases 1–2 change
nothing a user can see. That is deliberate — the risky parts (SSE under Fastify,
cross-replica fan-out, auth on a long-lived connection) are proven with `curl`
and contract tests before any UI depends on them. A failure in Phase 2 is a
localized problem; the same failure discovered during Phase 3 is entangled with
UI work.

**Increments after the MVP**: US2 (live analytics) is the highest value per
task. US3 and US4 harden rather than extend, and either may ship independently.

**Deferred by the spec, not forgotten**: retrying a failed workout is out of
scope here — dismissal (T031) exists so the user is never stuck. DOM-level
component testing likewise stays out; T002 sets up pure-logic testing only.
